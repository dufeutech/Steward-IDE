# pack-publisher-pipeline

## Why

The asset-pack client side is complete and merged: the app verifies TUF metadata, downloads
blobs, and activates pack versions — but nothing on Earth can *produce* a signed repository
for it to consume. The updater is dormant (no endpoint, no embedded trust root), the TUF
path has never been exercised end-to-end (archived `asset-pack-system` tasks 6.1 and 7.3
carry explicit UNVERIFIED remainders), and a fresh clone cannot even boot because the
baseline pack payload is regenerated by hand from a README checklist. This change builds
the publisher half: the pipeline that turns a pack payload into a signed, hosted, fresh
release — and the proof that a real client accepts it.

## What Changes

- A publisher pipeline that takes a pack payload and produces the complete signed
  repository the client already expects (metadata + content-addressed targets), replacing
  the hand-run lab script.
- The repository is published to a static host and kept **fresh**: release metadata is
  re-signed on a schedule so clients can distinguish "no updates" from a freeze attack,
  per the existing `pack-update` requirements.
- Publishing runs in CI, not on a developer machine: the online signing key lives in the
  CI secret store, releases carry build provenance attestations, and freshness re-signing
  is a scheduled job.
- Baseline regeneration becomes a first-class tool using the same pipeline stages
  (fetch payload → generate manifest → verify against committed manifest), so a fresh
  clone can produce a bootable `packs-baseline/` deterministically.
- The dormant updater is activated: app config gains the update endpoint and the signed
  root of trust ships as an embedded resource.
- A signed-repository test fixture and an end-to-end updater test close the UNVERIFIED
  remainders — the client-side TUF path is finally exercised against a real signed
  repository in CI.
- ADR revision: the "update endpoint" hosting decision is re-examined — the previously
  rented host cannot serve the client's nested target paths (flat asset namespace), which
  the original ADR did not catch.

## Capabilities

### New Capabilities

- `pack-publish`: the publisher side of the pack-update contract — producing a signed
  release description and content tree that conforming clients verify and accept;
  maintaining metadata freshness over time; custody and rotation of signing keys;
  attaching build provenance to what is published. Critical concerns here (repository
  signing/creation tooling, key custody, hosting, provenance attestation) are
  build-vs-adopt decisions deferred to `/ai:decide`.
- `baseline-regen`: deterministic regeneration of the embedded baseline pack from its
  external origin — a fresh clone reaches a bootable state with one command, and a
  payload that does not hash-match the committed manifest is refused, never silently
  accepted.

### Modified Capabilities

_None._ The client-side specs (`pack-update`, `pack-manifest`, `pack-store`,
`asset-serving`, `baseline-boot`) already state the requirements this change must satisfy;
this change makes their publisher-side counterpart real and verifies the existing
requirements end-to-end. Activating the updater is configuration, not a requirement change.

## Impact

- **New tooling**: publisher CLI stages under `scripts/` (promoted from
  `scripts/py/lab/gen_pack_manifest.py`, which is retired by this change).
- **CI**: new publish workflow and a scheduled freshness re-sign workflow; a CI secret
  for the online signing key; provenance attestation on releases.
- **Hosting**: a static file host serving the signed repository tree (ADR revision — see
  What Changes).
- **App**: `app/src-tauri` gains the embedded trust-root resource and the update endpoint
  in `config/app.config.json` — activating code that already exists; the client contract
  (repository layout, target naming) is already fixed by `adapters/tuf_source.rs` and
  must not change unless the hosting ADR forces it.
- **Tests**: signed-repo fixture + end-to-end update test in the app's test suite.
- **Docs**: architecture diagram gains the publisher half (Rule 1); `packs-baseline/README`
  checklist replaced by the tool invocation; `DECISIONS.md` gains the new ADRs.
